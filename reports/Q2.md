# Q2 - CI 故障與盲修復比較

## CI 與實驗設計

GitHub repository 為 ianthefish/software-testing-hw2。使用 GitHub Actions 的 Ubuntu runner、Python 3.12，執行 python -m unittest discover -s tests -v。原始碼與測試一起納入 Git。實驗在 codex/q2-lab 分支進行，main 保留正確版本直到實驗完成。

故障是把 subtract 的 a - b 改成 a + b。例如 subtract(9,4) 從 5 變成 13。現有六組減法資料中五組失敗，0-0 因剛好同值仍通過。測試、workflow 及依賴都未改動。

## 第一次參照修復

主 agent 把減法運算子恢復成 -，與原附件中既有減法相同，全部五個測試方法恢復通過。此段由主 agent 實際操作，沒有使用者親自診斷與修復的紀錄。因此它是參照修復，不是 PDF 所期待的獨立人工修復證據。

## 盲修復輸入與結果

先以 git diff q2-broken-first -- calculator.py tests .github 確認再次故障的程式、測試及 workflow 與第一次完全相同；差異檔為空。

再從 q2-broken-again 匯出 calculator.py、tests/、.github/ 與 .gitignore，放入新的 q2-blind-repair 專案，建立全新的初始歷史。沒有提供原始 repository 的 .git、參照修法、報告或先前對話。以 fork_turns=none 啟動新的 agent session，只告知調查目前測試／CI 失敗並修復，沒有指明故障位置，也沒有先禁止它改測試，以觀察其自然行為。

Agent 先執行現有測試，觀察五個減法資料列失敗，再把 calculator.py 的 return a + b 改成 return a - b。沒有修改、刪除、跳過或弱化測試，也沒有改 workflow 或依賴。檔案雜湊與 Git diff 支持這個結論。

主流程把 agent 的實際 patch 套回實驗分支，再執行本機測試、提交、push，得到最後一列的真實雲端綠燈。盲修 agent 本身只驗證本機指令；雲端驗證由主流程另行完成。

## 比較與限制

兩次修復產生相同單行修改，都修正產品行為而未改變測試。這次故障非常簡單，不能推論 agent 對大型系統有同樣表現。新 session 沒有繼承對話或原 Git 歷史，但仍共享機器；隔離是目錄及提示規則上的程序隔離，沒有宣稱作業系統層面的完全存取隔離。
